# 配额用完不结束，改为值守待命

## Status

accepted（2026-10-30，spec 0003）。

## Context

投递配额与评估上限原来是「终止当日任务」的开关：命中即 `finish()`，worker 线程退出。但这两个上限约束的是「今天不再找岗位」，而投递后的当天下午恰恰是 HR 回消息最密集的时段——消息全部无人应答，等于把投递的产出丢掉一半。同时，时段结束原本也直接收工，导致「昨天晚上点的启动，今天早上必须重新点一次」，与「启动是总开关」的使用模型冲突。

## Decision

1. 配额、评估上限、组合耗尽三种原因只中止**扫描**，Run 进入新的进行态 `STANDBY`（值守待命），继续按巡检间隔回复未读消息，直到时段结束、用户停止或故障。
2. 时段结束不再收工，而是**挂起**（`WAITING_DUTY`）：收起页面（不导航、不刷新、不点开、不发消息），但值守期不结束；下一个窗口打开由既有调度唤醒，跨自然日时复位组合队列重新扫描。
3. 重启不自动接管（正在扫描/待命的 Run 仍标 `FAILED / SERVICE_RESTART`），挂起态跨重启保留。

## Considered Options

- **另起一条独立值守进程**：被浏览器档案独占锁否掉——`launchPersistentContext` 的 profile 第二个进程起不来，而且两个进程各自持有登录态会互相踩。
- **改成全局定时任务，与扫描并行**：被 `PlaywrightExecutor` 单线程否掉。并行意味着两个线程交替操作 `listPage` / `threadPage`，而 `BossAdapter` 是单例持有这两个页面字段，历史上这类并发正是「导航被打断成 `net::ERR_ABORTED`」的来源。
- **加一个「配额用完是否继续值守」的开关**：两套行为都可能出错，且「配额用完到底还回不回」会变成每次排查都要先问一句的前置条件。直接改默认，想彻底结束就点停止——那个按钮已经在。

## Consequences

- `QUOTA_REACHED` 不再作为 `run.status` 写入（枚举保留，历史数据要能读）；演练模式 `RunService.finishDryRun()` 的 QUOTA 分支仍以字符串 `QUOTA_REACHED` 作为 `terminal_reason`，状态本身是 `COMPLETED`。`COMPLETED` 的新写入来源只有演练跑完组合，`DUTY_END` 属历史数据（与 `spec/0003` 口径一致）。
- 一次值守期可以跨多天存在，`uk_run_running` 必须把 `STANDBY` 纳入，否则同一平台可能出现两个浏览器持有者。
- 浏览器在整段值守期内常开。这是「重启后不自动接管」能成立的前提——页面状态一直没断，才有资格谈复用；代价是跨夜的内存占用没有数据。
- 值守的可靠性与扫描解耦后，「它在不在跑」变成了必须显式表达的东西：`run.current_action` + `last_activity_at` + 定时心跳日志，三者缺一，等待与卡死在界面上无法区分。
- 待命期的消息延迟被巡检间隔钉住（默认 120 秒）。平台没有推流接口，这个上限是物理的，不是实现选择。
