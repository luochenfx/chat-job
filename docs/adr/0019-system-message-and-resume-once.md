# 系统消息不作为回复依据；简历同一会话只发一次

## Status

accepted（2026-11-06）。落在 `Models.ChatMessage.system`、
`ReplyRuleEngine.Action.SKIP_SYSTEM`、`ReplyStore.resumeAlreadySent`。

## Context

2026-11-06 上午两起事故，同一类根因的两个面：

1. **09:39–09:52，同一个 HR 收到三份简历。** 第一次「方便发一份你的简历过来吗」正常命中
   「简历索取」并发出。随后平台播报两条回执：「对方已查看了您的附件简历」
   「对方已同意，您的附件简历已发送给对方」。两条都含「简历」，被当成 HR 的新消息整条命中
   同一条规则，于是又发了两份。回执是本系统自己动作的产物，却成了自己的输入。

2. **10:17，对方发来一张索要简历的卡片，判定成「消息为空或是图片」。** Boss 的卡片消息里
   没有 `.text` 节点（实测 `hasTextEl=false`，卡片结构是 `message-card-wrap` 一类），
   `readMessages` 只读 `.text`，读到的就是空串。于是一次真实的索要没有触发任何动作，
   AI 还给出了「对方发的是非文字消息 看不到内容没法接」。

`docs/tech/0002` 的 F15 早就写明 Boss 的 DOM 用 `item-myself` / `item-friend` /
`item-system` 三分归属，C12 也把「系统消息可能在带文本时被误当 HR 消息」列为未取证的
风险项。这次是那条风险真的发生了。

## Decision

1. **卡片正文要读。** `BossAdapter.readMessages` 在 `.text` 为空时回落到消息项的整块可见
   文本，并去掉 `.item-time` 时间分隔。按钮字（「发送简历」「点击预览附件简历」）刻意保留：
   只挑标题节点会在下一次改版时又读成空，把同一类漏读再犯一遍。

2. **系统消息单独成维，不参与判定。** `ChatMessage` 增加 `system`，判据是
   「Boss 的 `item-system` 类名 **且正文来自文本节点**」。判定引擎在「自己发的」之后、
   敏感词与关键词之前整条跳过（`SKIP_SYSTEM`）。它既不是对方说的话，也不是我打的字，
   但它带着对方说话时的关键词 —— 所以只能整条不看，不能靠关键词表规避。

   第二个条件（正文来自 `.text`）不能省：Boss 的卡片也会挂在 `item-system` 上
   （`BossSelectors.RESUME_CARD` 的实测记录里，我方发出的绿色简历卡片就是 `item-system`）。
   只按类名判，会把「对方索要简历的那张卡片」一起跳过 —— 那正是这次要修的另一半。
   播报类回执是文本模板，一定带 `.text`；卡片一定没有 `.text`，这一刀切得干净。

3. **简历同一会话只发一次。** 判据是 `reply_log` 里已经有 `REPLY_RESUME`：那一行只在
   「简历卡片真的出现」时写，点失败、按钮是灰的、AI 降级都不写。所以它挡得住重复发送，
   又不会挡住「上次没发成功」的重试。已经发过时处置与「按钮不可用」同形：
   有兜底文案就发一句，没有就静默收尾。

4. **关闭态也改。** 这是对 spec 0002 §2.1 第 1 条（「关闭即与改造前逐行一致」）的有意偏离：
   这两条是缺陷修复，不是「顺手优化」。逐行一致要保住的是「AI 能力不泄漏进关闭态」，
   而不是把一个会把三份简历发给同一个 HR 的行为原样保留。

## Consequences

- `reply_log.action` 新增取值 `SKIP_SYSTEM`。它不进「未命中」列表：那是「需要人补规则」
  的一栏，而这是一次正常跳过。
- 系统消息不再计入效果采集的 HR 条数与岗位质量判断的 `hrMessages`。原来一条
  「已查看简历」的回执就能把「沟通深度」抬到评估线上，白花一次模型调用。
- AI prompt 与质量判断的对话记录里，系统消息标成「系统」，不冒充任何一方。
- 智联的消息节点上没有取证到系统消息类名（`docs/tech/0002` C12：采样会话
  `item-system` 均为 0），那里 `system` 恒为 `false`；兜底是第 3 条，不是猜一个类名。
- 卡片正文现在会参与规则匹配，这是第 1 条换来的代价：职位卡片、名片这类消息里的字
  （例如职位描述里的「简历」）也可能命中「简历索取」。已知的三道闸是「同一会话只发一次」、
  「发简历是确定性动作、不经过模型」、以及发完简历后 3 分钟的会话冷却（我方简历卡片的回显
  落在冷却窗口内，不会被当成新索要）。如果真实运行里出现误发，应当收紧规则关键词
  （把「简历」换成「简历发我」「发一份简历」这类更具体的说法），而不是把卡片正文再读回空。
