# 每个平台一条独立流水线，并行运行

## Status

accepted（2026-10-30，spec 0004；事实依据已并入本文 Context 与 Considered Options）。

## Context

以下描述的是 2026-10-30 决策前的状态；当前已按本文 Decision 完成多平台改造，实施记录见 `spec/0004`。决策前系统只能跑一个平台，这个限制不在数据库，而在五处 Java 单例：

- `PlatformAdapter` 只有 `BossAdapter` 一个实现，以单值注入；
- `BrowserSession` 单例，一份 `context`、一个 `userDataDir`；
- `PlaywrightExecutor` 单例，一条 `playwright-thread`；
- `RunService` 单例，`worker` / `stopRequested` / `pauseRequested` / `dutyEnded` / `currentRunId` / `pausedFrom` 六个字段全是「只有一个任务」的假设；
- 前端「当前任务」接口是单数。

但数据库从第一天起就是按平台隔离的：`uk_run_running ON run(platform)`、`uk_unread_task_open(platform, …)`、`uk_conversation(platform, …)`、`uk_job_posting(platform, …)`、`uk_daily_counter(platform, day)`、`uk_platform_config(platform)` 六个唯一键都带 platform。`uk_run_running` 的迁移注释原文是「它是**持有浏览器的那一个**的状态之一」——这条索引算的从来就是「每个平台一个持有者」，从没要求全库只有一个。

现在要接智联，之后还会有第三、第四个。所以真正要决定的是：**多个平台之间排队（串行）还是各跑各的（并行）**。

这里有一个容易漏掉的结构事实：**值守嵌在扫描循环里**（`processCards` 每 5 张卡片或每 120 秒调一次 `sweep`）。所以「扫描并行 + 值守串行」不是一个可以自由挑选的组合——扫描一旦并行，值守就自动并行了；要让它串行，必须加锁。

**并行评估依据（原调研稿结论，已并入本文）**

Playwright Java 要求对象在创建它的线程上调用，因此每平台各一条线程、各持自己的对象，是满足该约束而不是绕过它。三种方案的取舍依据：并行的收益来自结构，随平台数增长；串行省一半 AI 调用属于经济性收益，不随平台数增长。平台数到 4 时，串行的耗时与轮转复杂度线性上升，并行只是多几个进程。不预设并发信号量，内存不足时按「平台开关 → 并发上限 → 重做架构」的顺序处置。`ai_config` 是全局单行表，`ai_reply_max_per_sweep` 两个平台共用同一个数；并行后每平台各建一份预算，一轮最多消耗配置值的平台数倍，本轮只改配置页文案。

## Decision

1. **每个平台一条独立流水线**：自己一个浏览器 profile 目录、自己一条 Playwright 线程、自己一个任务实例。平台之间不共享任何运行时状态。
2. **平台差异只允许出现在 `PlatformAdapter` 的实现里**。编排层（扫描主循环、值守、评测、投递判定）不允许出现 `if (platform == "boss")` 这类分支。这是现有 `PlatformAdapter` 注释里已经写下的意图，本 ADR 把它升格为约束。
3. **值守不另起线程、不另起进程**，仍复用本平台这条流水线的浏览器上下文。ADR-0002 的结论保留，只是作用域从「全局」缩到「每个平台」。
4. **AI 调用预算的语义改为「每个平台各自的上限」**。`ai_config` 是全局单表，`ai_reply_max_per_sweep` 两个平台共用同一个数，并行后 `AiBudget` 每平台各建一份，一轮实际最多消耗配置值的 N 倍（N = 平台数）。只改配置页文案，不引入跨平台共享预算机制 —— AI 只在有未读时才花钱，两边同时有大量未读恰恰是最需要它快的时刻。
5. **不做并发信号量**，不设「同时最多开几个浏览器」的机制。内存吃紧时的处置顺序：配置页加平台开关 → 才考虑并发上限 → 最后才重做架构。
6. **值守里「对方索要简历 → 点同意发出简历」不占投递配额**，具体见 ADR-0004。

## Considered Options

- **串行轮转（一个 worker 轮流跑各平台）**：要引入「轮转调度器」——谁先谁后、每平台跑多久、卡住怎么切走、公平性怎么保证。这是**一个全新的概念**，而且必须住进 `RunService`（现约 1400 行，6 个字段是单任务假设）。更关键的是它会饿死：平台 A 连跑两小时，平台 B 的 HR 消息就两小时无人应答——智联账号现在正躺着 21 条索要简历。它换来的收益只有一个浏览器省 400–600MB，而这个收益**不随平台数增长**：加到第四个平台时，串行的耗时与复杂度都线性上涨，并行只是多开几个进程。

- **并行但共用浏览器上下文（两个平台轮流用同一批标签页）**：被 `PlaywrightExecutor` 的单线程约束和 `uk_run_running` 的语义一起否掉。共用上下文意味着两条线程交替操作同一批 Page，历史上这类并发正是「导航被打断成 `net::ERR_ABORTED`」的来源（ADR-0002 已因同样的理由否掉过一个方案）。

- **并行但值守加锁串行**：能省一半 AI 调用，但用一把锁把两个平台的扫描串起来 —— 平台 A 卡在一个打不开的会话上时，平台 B 的扫描线程也跟着停。`ThreadTargetUnsafeException` 这个异常类型的存在本身就说明「会话打不开」是常态而非意外（Boss 侧选择器与页面结构对不上的历史故障高发区）。把一个平台的常态问题放大成全系统停摆，账算不过来。

## Consequences

- `PlatformAdapter` 从单值注入改为按平台取（`Map<String, PlatformAdapter>` 或限定符）；`BrowserSession`、`PlaywrightExecutor`、任务实例都改为每平台一份。
- **`userDataDir` 必须按平台分目录**。同一个 profile 有独占锁，第二个浏览器实例起不来 —— 这是**硬失败**，好在会立刻暴露而不是随机出错。连带代价：智联要在自动化 profile 里重新扫码登录一次（现有登录态在你日常浏览器里，本来就不能复用，所以这不是新增成本）。
- `RunService` 的六个单任务字段**不必改写**，改为按平台实例化（prototype + 一个 registry），内部代码一行不动。这是本次改造的最小改动路径。
- 前端「当前任务」从单数改为列表或带 platform 参数，`console/` 下对应页面同步。
- **日志必须带平台标识**。并行后两条时间线交错，没有前缀时「哪条日志是哪个平台」只能靠上下文猜。
- 企业微信通知会来两条（同一事件类型各平台各一条），文案必须带平台名，否则收到通知不知道是哪个平台出的事。
- **回复规则与敏感词目前没有平台维度**（`uk_reply_rule_name` 不含 platform），两个平台共用一套。智联的消息形态与 Boss 不同（「索要简历」是卡片动作而非文本），规则是否通用需要单独评估 —— 见 ADR-0004。
- 内存：同时开 N 个自动化 profile，每个约 400–600MB。这是本机桌面工具，机器扛不扛得住，用户开一个 Chrome 就知道，因此不预设并发上限。

## Open Questions

四条假设，都必须在智联实现的首个迭代里验证。任一不成立，本 ADR 的结论需要复议：

| # | 假设 | 若假设不成立 |
|---|---|---|
| 1 | 智联的未读数能从会话列表批量读到（实测每行有独立数字角标） | 若必须点开每个会话才知道有没有未读，值守的成本模型要重算，「并行值守」的性价比会变化 |
| 2 | 智联的投递入口只能在岗位详情页（实测列表卡片上无任何按钮） | 若卡片上出现投递按钮，扫描路径能变快，但架构不变 |
| 3 | 智联的聊天工具栏上和 Boss 一样有「发简历」按钮；卡片上的「同意」是等价备用路径（用户陈述） | 若工具栏没有但卡片「同意」在，切换为点卡片；两者都没有，ADR-0004 的被动路径在智联落不了地 |
| 4 | 一个 profile 目录只能被一个浏览器实例持有（Chrome 硬约束） | 由「第二个起不来」这个硬失败兜底，不需要额外设计 |

## Open Questions 结论（2026-10-31 回填，阶段 3）

四条都验过了，但**验到什么程度不一样** —— 下面按「成立 / 未取证」分开写，不把「代码就位」当成「真实发生过」。

| # | 结论 | 依据 | 是否要复议本 ADR |
|---|---|---|---|
| 1 | **成立，但样本极小** | 实现按会话行的角标读未读（`ZhaopinAdapter` 的 `IM_SESSION_BADGE`）；真实值守里智联的会话被识别为未读并进入处理，落了 1 条 `AI_SKIPPED`。但当时账号里只有 1 个会话，「批量」这个前缀没被压到 | 否。真到几十条未读时再看一轮耗时，那是调优不是架构 |
| 2 | **成立** | 阶段 1 实测：列表卡片上没有任何投递按钮，投递只在详情页的「立即投递」（见 spec/0004 阶段 1 实施记录） | 否 |
| 3 | **未取证** | 代码按工具栏按钮走，且带置灰降级（读 `aria-label` 里的平台原因返回 `UNAVAILABLE`，见 `ZhaopinAdapter.sendResume`）；但**全库 `reply_log` 里 `REPLY_RESUME` 是 0 条** —— 两个平台都从未真实触发过一次 | 暂否（降级路径已就位）。**下一次智联真有 HR 索要简历时必须补验**，那时若两条路径都不可用，ADR-0004 的被动路径在智联落不了地，需要回来复议 |
| 4 | **成立** | 2a 之后两个 profile 各自起一个实例、同时存活（`bsk browsers` 同时列出两个自动化实例，分别停在 `zhaopin.com` 与 `zhipin.com`）。同一约束的另一面也见到了：强杀后残留的 msedge 子进程占着某个 profile 时，该平台后续每次启动都报 `session closed` | 否 |

阶段 3 顺带补了一条本 ADR 第 5 条交给它的东西：**平台开关**。`platform_config.enabled` 从「只读显示」变成真的闸门：

- 停用的平台不再被拉起浏览器（闸门在 `BrowserSession.ensureReady()`，是启动链路唯一必经点）；
- 不再新建任务，也不被 30 秒的唤醒轮询叫醒；探测登录 / 打开登录页 / 自检一律 400；
- 还有未结束任务时不允许停用（否则开关关掉的只是「下一次启动」，当前那条还在跑）；
- 停用的同一刻收掉它已开的浏览器 —— 这正是「不再开第二个浏览器」要的效果。

取证：停用智联后，四个入口全部返回 400 且文案点名「智联招聘」；随后只启用 BOSS 并打开登录页，进程里只有 `browser-data\boss` 那棵树（13 个 msedge，zhaopin 为 0），`bsk browsers` 只列出 BOSS 那一个自动化实例。
